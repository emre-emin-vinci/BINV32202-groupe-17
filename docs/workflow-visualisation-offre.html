Visualiser une offre, du composant React jusqu'à SQLite… puis retour

Cette page décrit le parcours complet d'une requête GET /offers. L'utilisateur ouvre la page des offres, le frontend appelle l'API, le backend vérifie les droits et interroge la base, puis la réponse remonte jusqu'au tableau React.

Un aller-retour, pas une seule direction

La requête descend du navigateur vers SQLite pour trouver les données. La réponse remonte ensuite sous forme de JSON : le controller la renvoie, le service frontend la valide, le hook met à jour son état et React reconstruit le tableau visible.

Le workflow détaillé

Chaque étape a une responsabilité précise afin de séparer l'interface, le métier et l'accès aux données.

1

L'utilisateur arrive sur /offres

App.tsx vérifie la session via useAuth. Si l'utilisateur a le droit de consulter les offres, React rend OffersPage avec le token et le callback de déconnexion.

Voir le lien entre les composants 
App
  └─ OffersPage
       └─ useOffers(token, onUnauthorized)
            └─ getOffers(token)
2

Le hook démarre le chargement

useOffers initialise l'état isLoading, crée un AbortController, puis appelle le service HTTP dans un useEffect. La page peut donc afficher un état de chargement. 

const { offers, isLoading, error } =
  useOffers(token, onUnauthorized);
3

Le frontend envoie la requête à l'API

Le service appelle /api/offers avec le token dans l'en-tête Authorization. Vite utilise son proxy pour retirer /api et transmettre la requête au backend sur le port 3000. 

GET http://localhost:5173/api/offers
Authorization: <token>

→ GET http://localhost:3000/offers
4

Le backend authentifie la requête

Le middleware authenticate vérifie le token, recharge l'utilisateur en base et place son identité, ses rôles et ses entreprises dans la requête. Un token absent ou invalide produit une réponse 401.

5

La route vérifie l'autorisation

Le controller utilise authorize(canListOffers). Le backend ne se fie pas à l'interface : il décide réellement si l'utilisateur peut consulter les offres. Sinon, il renvoie 403 FORBIDDEN.

6

Le service applique la visibilité métier

Le service construit un filtre selon le profil : toutes les offres pour un administrateur, les offres PUBLISHED pour un étudiant et les offres déposées par le contact pour un déposant. 

admin   → {}
student → { status: "PUBLISHED" }
contact → { depositorContactId: user.id }
7

Le repository interroge SQLite

Le repository transforme le filtre en paramètres SQL. Il joint les tables des entreprises, années académiques et périodes pour préparer les données nécessaires à l'affichage. 

SELECT o.id, o.title, o.description, o.status,
       c.short_name AS company_short_name,
       ay.label AS academic_year_label,
       p.code AS period_code
FROM offers o
JOIN companies c ON c.id = o.company_id
JOIN academic_years ay ON ay.id = o.academic_year_id
JOIN periods p ON p.id = o.period_id
WHERE ...;
8

Les données remontent dans le backend

Le repository renvoie des lignes SQL (DBO). Le mapper toOffer les convertit en objets métier, puis toOfferDto prépare le format public de l'API. Le controller renvoie la liste avec res.json(...). 

SQLite rows
  → toOffer(row)
  → toOfferDto(offer)
  → HTTP 200 + JSON
9

Le service frontend valide la réponse

readJson vérifie le statut HTTP et le type du JSON avec isOfferList. Une réponse mal formée devient une erreur explicite au lieu d'être affichée comme une liste valide.

10

React met à jour l'interface

Le hook stocke les offres dans son state. OffersPage choisit alors entre chargement, erreur, liste vide ou OfferTable. React rerend le tableau avec les données reçues.

Le retour des données vers l'écran

Après l'exécution SQL, chaque couche restitue un format adapté à la couche suivante. Cette séparation évite de mélanger SQL, HTTP et affichage.

Base de données

Lignes SQLite

SQLite fournit des colonnes issues de offers et de ses jointures, avec des noms adaptés au stockage.

Backend

Objet métier puis DTO

Les mappers convertissent les données brutes en objet Offer, puis en format public stable pour l'API.

HTTP

Réponse 200

Express sérialise la liste avec res.json. Le navigateur reçoit un tableau JSON ou une erreur structurée.

React

État puis affichage

Le hook enregistre les offres et OfferTable affiche chaque titre, entreprise, période et statut.

Exemple de données à chaque frontière

Les noms peuvent changer entre la base et l'interface : les mappers et les guards rendent ces transformations explicites.

Réponse JSON réelle de l'API

Décision d'affichage

  • Chargement : LoadingState informe l'utilisateur.
  • Aucune offre : EmptyState explique que la liste est vide.
  • Erreur : ErrorState affiche un message lisible.
  • Données valides : OfferTable rend le tableau.

Responsabilités et erreurs

Ce que fait chaque couche

  • Page / composant : affiche l'interface et les états visuels.
  • Hook : orchestre le chargement, l'annulation et l'état React.
  • Service frontend : réalise l'appel HTTP et valide le JSON.
  • Controller : traduit HTTP vers le service métier.
  • Service backend : applique les droits et règles de visibilité.
  • Repository : exécute le SQL sans décider des permissions.
  • Mapper : convertit les formats de données.

Cas d'erreur principaux

  • 401 : session absente ou invalide ; le frontend déconnecte l'utilisateur.
  • 403 : utilisateur authentifié mais sans droit d'accès.
  • 404 : route inconnue ; le middleware de routes introuvables répond.
  • 500 : erreur inattendue ; errorHandler centralise la réponse.
  • Réponse JSON invalide : le guard frontend affiche une erreur de chargement.
